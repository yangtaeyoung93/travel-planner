# harness-design skill

작업을 **역할**로 쪼개고, **파일 인계**와 **검증 게이트**로 잇는 에이전트 팀을 설계한다.

## 사용하지 않는 경우

- 한 에이전트가 한 번에 끝낼 수 있는 작업 (팀은 오버헤드다)
- 이미 있는 하네스를 돌리거나 점검하는 작업

## 설계 절차

1. **작업 분해**: 입력, 산출물, "완료"의 판정 기준을 한 줄씩 적는다. 판정 기준이 없으면 게이트를 만들 수 없으므로 먼저 정한다.
2. **아키텍처 선택**: 아래 표에서 고른다.
3. **에이전트 정의서**: 에이전트마다 역할 1개, 입력 파일, 출력 파일, 허용 도구를 적는다. 역할이 겹치면 합친다.
4. **스킬 분리**: 팀을 호출하는 절차(오케스트레이션)는 스킬, 개별 역할은 에이전트로 둔다.
5. **오케스트레이터**: 호출 순서, 인계 파일 경로, 판정 분기, 재시도 상한, 상한 초과 시 동작을 쓴다. 상세는 `harness-orchestrator` 스킬을 따른다.

## 아키텍처 선택

| 상황 | 구조 |
|---|---|
| 만든 결과를 검증해야 함 | 생성 → 검증 루프 (PASS/REDO) |
| 단계가 앞 결과에 의존 | 순차 파이프라인 |
| 같은 일을 대상별로 반복 | 팬아웃 (병렬) 후 종합 |
| 관점이 여럿이고 이견이 생김 | 팬아웃 → 질문 → 재확인 → 재평가 |

## 필수 규칙

- **인계는 파일로 한다.** 에이전트 간 전달은 `_workspace/*.md` 같은 고정 경로에 쓴다. 대화에 의존하지 않는다.
- **저장을 프롬프트에 명시한다.** 서브에이전트는 요청받지 않으면 리포트 파일을 만들지 않는다.
- **판정 파일이 없거나 불명확하면 REDO로 처리한다.**
- **재시도 상한을 둔다.** 초과 시 마지막 결과와 "수동 검토 권장" 경고를 사용자에게 보인다.
- **공유 자원은 직렬로 잠근다.** 브라우저·DB처럼 동시 사용이 위험한 도구는 한 번에 하나씩 쓴다.
- **금지 행동을 정의서에 적는다.** 결제·로그인·삭제 같은 되돌릴 수 없는 동작은 명시적으로 막는다.

## 예시: 이 프로젝트의 두 하네스

- `commit-message`: author → reviewer → 판정 분기 (REDO 최대 2회). 생성/검증 루프.
- 동유럽 조사: 8곳 병렬 조사 → 브라우저 검증(직렬) → 6명 분석 → 질문 사이트만 재확인 → 보고서. 팬아웃 + 토론.

## 흔한 실수

| 실수 | 해결 |
|---|---|
| 에이전트 역할이 겹침 | 입력·출력 파일이 같으면 하나로 합친다 |
| 검증자가 없거나 판정 기준이 모호 | 판정 형식(PASS\|REDO + 사유)을 먼저 정한다 |
| 모든 결과를 대화로 전달해 컨텍스트가 폭증 | 파일로 쓰고 경로만 넘긴다 |
| 재시도 무한 반복 | 상한과 초과 시 동작을 정의한다 |
